## Design Specificity Verdict

**LLM assessment (Assessment A):** Grounded, not interchangeable. Sets×reps-range notation, inline per-exercise rest durations, a "PREV 6×100kg" chip pulled from real history, a PR badge from computed previous-bests, a rest-timer sheet that drives session rhythm, kg/lb unit toggling threaded through every number, and template target-auto-sync logic that only ever raises targets after a workout — this is a purpose-built lifting app, not a generic CRUD list with icons.

**Deterministic scan (Assessment B):** `detect.mjs --json src` returned exactly **1 finding**, a warning: `overused-font` on `src/index.css:67` (`body { font-family: "Inter", ... }`). Verified accurate — the whole app body uses Inter with a generic sans-serif fallback and no distinctive display face outside the `Allerta Stencil` wordmark, which is deliberately reserved for hero moments only. Zero error- or info-severity findings.

**Contrast evidence (Assessment B, computed via getComputedStyle):** the same muted-gray text token (`rgb(148,148,148)`) passes WCAG AA comfortably everywhere it's checked (5.7–6.3:1) *except* on the active/highlighted exercise card during a workout, where its lime-tinted background drops the ratio to **2.65:1** — a real, measured AA failure on the `X/Y sets` label of whichever exercise the user is currently logging.

## Overall Impression

The product identity is real and consistent — this doesn't read as a template. The gap isn't visual polish, it's **destructive-action consistency**: one delete glyph means three different things depending which screen it's on, and the app's own established pattern (confirm dialog + "used in templates" guard) gets skipped in exactly the place editing a template happens. The single biggest opportunity is the Workout Complete screen, which is currently the flattest screen in the app despite being the one moment all the PR-tracking machinery is supposed to pay off.

## What's Working

1. **PREV/last-session chips** (`TemplateDetail`, `ActiveWorkout`) — pulling `6×100kg` from history to pre-fill the next set's steppers removes real friction; this is what makes the app feel grounded rather than a generic form.
2. **Draft persistence + nav-bar indicator dot** — a workout survives navigation, reload, and is signaled system-wide by a small dot on the Workout tab; the underlying code documents the specific race condition it guards against.
3. **Rest-timer sheet** — drag-to-collapse into a pill, milestone-only (not per-second) screen-reader announcements, and staying interactive under the exercise card underneath it is a genuinely well-considered mobile pattern.

## Priority Issues

**[P0] Edit Template's exercise-delete has no confirmation, unlike every other delete in the app**
- **Why it matters:** trains-then-punishes — a user who's used the confirm-gated delete in the Exercise Library will tap Edit Template's identical-looking red X with the same confidence and instantly lose an exercise's target-set/rest configuration, no recovery.
- **Fix:** route this X through the same `ConfirmDialog` already used by the Exercise Library and Add-Exercise picker, or add an undo toast at minimum.
- **Suggested command:** `$impeccable harden`

**[P1] Workout Complete fails the peak-end rule**
- **Why it matters:** this is the one screen where all the PR-tracking machinery pays off, and it currently renders identically whether or not a PR happened — three flat stat tiles and a "Done" button, visually weaker than the History screen the user lands on next. For a habit-forming fitness app this is the highest-leverage retention moment in the product.
- **Fix:** give a PR session real presence (the `prs: string[]` data is already computed, just not surfaced with any weight) — color, motion, or an explicit PR callout; give the base "complete" state more visual weight than a settings row.
- **Suggested command:** `$impeccable delight`

**[P1] Add-Exercise picker's delete-from-library X sits inside an "add" flow**
- **Why it matters:** task-context bleed — while trying to *add* an exercise (often mid-workout or mid-template-edit), the user is one mis-tap from opening a delete confirmation for a global library entry. The confirm dialog limits the damage but the affordance doesn't belong in this flow at all.
- **Fix:** drop the delete affordance from the picker; library management already lives in, and is well-handled by, the Exercises tab.
- **Suggested command:** `$impeccable distill`

**[P2] "Start" doesn't distinguish resume-with-existing-draft from a genuinely fresh start**
- **Why it matters:** verified live — after backing out of an active workout, `TemplateDetail` still shows plain "Start" even though the nav-bar dot confirms a draft exists; tapping it does correctly resume, but nothing on that screen told the user that in advance, so they have to trust a dot on a different tab.
- **Fix:** swap the label to "Resume" (with elapsed time) whenever `getActiveWorkoutDraft()` matches the open template — the check already exists elsewhere in the codebase, this just needs to run here too.
- **Suggested command:** `$impeccable clarify`

**[P3] TemplatesScreen's row packs 4 competing controls into one 44px band**
- **Why it matters:** drag handle + 2 chevrons + full-row tap target compete for thumb space against the one action that actually matters (opening the template) — most exposed in the common single-template state, where the reorder controls are pure dead weight.
- **Fix:** hide reorder affordances when there's only one template, or collapse drag+chevrons behind an explicit edit-mode toggle.
- **Suggested command:** `$impeccable layout`

## Persona Red Flags

**Alex (Power User):** the chevron-reorder method holds up for 2-3 templates but gets tedious past ~10; no multi-select, no template duplication, no keyboard-only path beyond the chevrons.

**Sam (Accessibility-Dependent User):** the timer's milestone-only screen-reader announcements and the documented WCAG contrast fix elsewhere in `index.css` show real prior care — but that care wasn't extended everywhere: the measured **2.65:1 contrast failure** on the active-exercise card's `X/Y sets` label (Assessment B, computed) is exactly the kind of regression Sam would hit reading her own current set count mid-workout. The rest-timer's drag-to-collapse gesture also has no visible keyboard equivalent, unlike template reorder, which explicitly added chevrons for this reason (SC 2.5.7) elsewhere.

**Casey (Distracted Mobile User):** the undo-less Edit Template delete X and "Delete template" sitting at equal visual weight next to rename/reorder are exactly the high-consequence, low-friction targets that punish a distracted thumb — Casey is the persona most exposed by the P0 finding above.

## Minor Observations

- "Sign out" on Profile renders in the same saturated red as every destructive action, despite being low-stakes and reversible — dilutes red's meaning elsewhere in the app.
- WorkoutHomeScreen and post-workout History both have a large amount of unused vertical space below the fold on a phone-sized viewport (content ends ~40% down an 812px viewport).
- The PR badge's amber/gold is a deliberate departure from the primary lime accent — good semantic differentiation, worth preserving rather than homogenizing in any future color pass.
- One reported anomaly from Assessment B, **unconfirmed**: a set appeared to show as already logged (`1/10 sets`) immediately after tapping "Start," before any explicit log action. Assessment B itself flagged this as possibly a misread or environment artifact rather than a confirmed bug, and a second, isolated multi-tab test could not reproduce a related draft-visibility glitch. Worth a deliberate, isolated re-check before treating as real — see the questions below.

## Questions to Consider

1. Is the "Start" vs. "Resume" gap a copy oversight, or does it suggest the draft-resume mental model was designed nav-bar-first (the dot) without walking through what the user actually sees on the screen where they'd act on it?
2. The app has clearly invested in one consistent delete pattern (`ConfirmDialog` + "used in templates" guard) — was Edit Template's unguarded delete a deliberate speed-over-safety tradeoff, or did it just not get the same pass the other two delete sites did?
3. If PRs matter enough to compute and badge in three different places (Workout Home, History, the badge system itself), why does the one screen where a PR is *earned* treat it identically to a non-PR session?
