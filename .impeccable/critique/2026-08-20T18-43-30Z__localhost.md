## Design Specificity Verdict

**Assessment A (LLM):** Specific, not generic. The reps×weight shorthand is real lifting notation, the log-set control is entirely stepper-driven (no keyboard needed with a chalked/sweaty thumb), the rest-timer is a full-sheet takeover sized to be read at arm's length, and the type system enforces its own restraint via an explicit code comment reserving the stencil face for hero moments only. PR badges get a deliberately separate hue from the primary CTA "so a PR badge... doesn't share a hue with the primary CTA." None of this transfers to an unrelated product unchanged.

**Assessment B (deterministic):** The CLI scan (`detect.mjs --json src`) returned exactly one finding across the whole tree — `overused-font` on Inter (`index.css:59`), warning severity. Verified accurate (Inter genuinely is the global body font), but low-impact in context: Inter plays the quiet workhorse role here, subordinate to the stencil/mono pairing that actually carries the identity. No other systemic drift detected.

**Where they agree:** both independently concluded this is a coherent, product-specific system, not template UI wearing a fitness skin.

## Overall Impression

The bones are unusually good for a solo/small-team build — real focus-management infrastructure, a genuine drag-alternative for reordering, pre-filled recognition-over-recall logging. What's missing isn't craft, it's a few load-bearing details: the one moment that's actually irreversible (Finish) gets less ceremony than the one that isn't (Discard), the single most time-critical number in the app (the rest countdown) is invisible to a screen reader, and there's no help layer at all for a first-timer trying to parse "PR" or a target rep range.

## What's Working

1. **Recognition over recall** (`ExerciseCard.tsx`): reps/weight steppers default to the exact next set from last session, with `PREV` chips showing the same numbers on the card being logged against. The strongest, most product-specific piece of design in the app.
2. **The Templates reorder pattern**: a drag handle *plus* explicit up/down chevron buttons, with a code comment citing WCAG 2.2 SC 2.5.7 — a rare instance of a team shipping the accessible alternative, not just the drag.
3. **`Modal.tsx`'s focus management**: real focus trap, Escape handling via a modal stack (so a `ConfirmDialog` nested inside `ExercisePicker` doesn't fight its parent for the same keydown), and focus restored to the trigger on close.

## Priority Issues

**[P1] Rest-timer countdown has no `aria-live` region.**
*Why it matters*: `TimerSheet.tsx`'s 88px countdown mutates via plain DOM text every second with no `aria-live` wrapper. A screen-reader user gets zero spoken updates of remaining rest time — for the single most time-critical number in the app, this is a real gap for a Sam-type user.
*Fix*: wrap the countdown in `aria-live="polite"`, throttled to announce at meaningful intervals (not every second), switching to `"assertive"` near zero.
*Suggested command*: `/impeccable harden`

**[P1] Finish is irreversible and silently mutates the template — Discard, which changes nothing, is the one that gets a confirmation.**
*Why it matters*: `handleFinish` commits the session *and* rewrites the template's `targetSets`/`restSeconds` with no dialog; `handleDiscard` (which discards unsaved local state) requires a full confirm. The friction is inverted relative to the actual stakes — someone who taps Finish by muscle memory after a lighter/heavier day gets their template quietly changed with no visibility into it.
*Fix*: surface a one-line summary before commit when Finish would change the template ("Bench Press's target will update to 5 sets — Finish?"), or at minimum show what changed on the Summary screen.
*Suggested command*: `/impeccable clarify`

**[P2] No persistent "workout in progress" indicator once you leave the Workout tab.**
*Why it matters*: verified live — navigating History → Workout resumes the draft correctly, but nothing on History/Templates/Profile or the nav bar itself signals a session is running; the Workout tab's icon looks identical idle or mid-set. A distracted (Casey-type) user who checks History mid-rest has no glanceable reminder they're still "in" a workout.
*Fix*: a small dot/pill badge on the Workout nav icon when a draft exists, distinct from its permanent lime-circle styling.
*Suggested command*: `/impeccable delight`

**[P2] Copy/verb mismatch on the highest-stakes dialog in the app.**
*Why it matters*: `ConfirmDialog`'s default `confirmLabel` is `"Delete"`; the Discard-workout call site never overrides it, so a dialog titled "Discard workout" resolves to a button labeled "Delete." Small, but it's exactly the moment where clarity matters most.
*Fix*: pass `confirmLabel="Discard"` explicitly at that call site.
*Suggested command*: `/impeccable clarify`

**[P2] Reorder up/down chevron buttons measure 28×22px — 2px under the WCAG 2.5.8 AA 24×24 floor.**
*Why it matters*: measured directly via `getBoundingClientRect()` on the live page. These are the accessible drag-alternative praised above (Strength #2) — the alternative itself has a small, genuine target-size shortfall neither Assessment A's read nor the earlier code-level audit caught; only direct browser measurement surfaced it.
*Fix*: grow the chevron buttons to at least 24×24 (28×24 keeps the current width).
*Suggested command*: `/impeccable adapt`

**[P3] Muscle-group picker shows ~1.5 of 18 options before scrolling.**
*Why it matters*: confirmed live via zoom screenshot on the "New exercise" modal — the scrollable listbox is tall enough for barely more than one row despite items being grouped under headers.
*Fix*: give the listbox a taller fixed height (~5-6 rows) before scroll kicks in.
*Suggested command*: `/impeccable layout`

## Persona Red Flags

**Casey (distracted, one-handed, mid-workout)**
- Collapsing the *expanded* rest-timer sheet requires a drag past an 80px threshold — no plain tap-to-collapse exists (only the already-collapsed pill supports tap-to-expand). Harder one-handed than a button would be.
- No in-progress indicator on the nav bar (P2 above) — bouncing to History mid-rest leaves nothing reminding Casey a set is waiting.

**Sam (accessibility-dependent)**
- The rest countdown has no `aria-live` region (P1 above) — the most time-sensitive number in the app is silent to a screen reader.
- Also genuinely well-served in most places: `IconButton`'s 44×44 target, the WCAG 2.5.7 drag-alternative on Templates reorder, and the contrast fix (verified by direct measurement: 5.74–16.82:1 across every muted/secondary/badge element sampled, all clearing AA) show real, deliberate accessibility work — just not yet reaching the timer.

**Jordan (first-timer)**
- Heuristic 10 scored 1 for a reason: zero help/documentation anywhere. "PR," target rep ranges, and what happens when you log past your planned sets are presented with no legend or first-use explanation.
- Counter-example in Jordan's favor: the Workout Home empty state ("Start a template to log your first workout" + one button) is genuinely clean — single message, single next action.

## Minor Observations

- Default `Button` height is 40px (`h-10`), under the 44px `IconButton` explicitly targets elsewhere in the same codebase — an internal touch-target inconsistency (already tracked as a P2 in the separate technical audit; the two reports agree here).
- Browser-overlay detection (clean, reload-then-inject runs) found 8 and 16 instances respectively of sub-11px functional text on two different screens (nav labels, badge text, "sets"/"prev" labels) — corroborates and quantifies the technical audit's px-vs-rem text-scale finding with concrete counts.
- Leftover test data (an "fdsa" template, 0 exercises) exists in the local Templates list — not a design finding, just a cleanup note.
- One detector run (mid-session, re-injected without a full reload) additionally reported `flat-type-hierarchy` and a `text-occlusion` finding; Assessment B determined and disclosed these were artifacts of the overlay's own leftover annotation elements being re-scanned, not real page defects — excluded from findings above.
- Assessment B's touch-target measurements were taken in an unintentional 1152×1838 desktop viewport (`resize_window` to a phone size didn't take effect) — however the app's own CSS pins its content to a fixed 430px-wide column regardless of window size (confirmed via this session's earlier screenshots), so the component-level pixel measurements above should still hold at real phone widths; only true responsive/orientation behavior outside that fixed column is unverified.

## Questions to Consider

1. If Finish is meant to feel like the casual, forward-moving action and Discard the scary one, why does Finish get to silently rewrite the user's template while Discard — which changes nothing — is the one gated behind a confirmation?
2. The rest timer is arguably the single most-glanced-at number in the app during real use — why does it get no live-region treatment when so much other accessibility groundwork (focus traps, drag alternatives, contrast fixes) has clearly already been done deliberately?
3. Given how much of the design's identity rests on "surface last session's numbers so nobody has to remember them" — why does that philosophy stop at the nav bar, where the user is left to remember, unaided, whether they still have a workout running?
